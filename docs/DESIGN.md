## 1. 产品定位

一款 **自托管、离线优先、多端同步** 的现代笔记应用，替代以云端为中心、数据难自控的传统笔记工具（如印象笔记）。

**核心差异化主张：**
- **数据自控**：全部数据存在自己的设备与自托管服务器，可随时迁移导出。
- **离线优先（Local-first）**：断网可用，联网静默同步，无网络时体验不受损。
- **极简 + Markdown 双轨**：支持所见即所得（WYSIWYG）极简正文，也支持纯 Markdown 源码。
- **从剪藏到沉淀**：浏览器一键剪藏网页，自动净化转 Markdown 入库。

**关键约定：**

- 附件以 `sha256` 为地址，跨设备去重，服务端按引用计数做 GC。

## 6. 同步引擎与离线（需求 2）

设计目标：**离线完整可用，联网后快速收敛，冲突不丢数据。**

### 6.1 本地 = 事实来源（Offline-first）
- 所有写操作只落本地 SQLite + 本地 Blob，立即返回，无网络也成功。
- 每个客户端维护一张 **Outbox（出站队列）** 记录待推送变更，与本地事务同提交（原子性）。

### 6.2 同步协议（增量，光标式）
```
客户端                         Go 服务端
  │  POST /api/sync/push           │
  │  {client_id, batch: [...],    │
  │    base_cursor}               │
  ├──────────────────────────────►│ 校验 base，逐条合并
  │◄──────────────────────────────┤ 返回 {applied, conflicts}
  │  POST /api/sync/pull          │
  │  {since_cursor}               │
  ├──────────────────────────────►│
  │◄──────────────────────────────┤ 返回增量+新 cursor + 服务器变更
  │                               │
  │  WebSocket (/ws/sync)         │ 推送"远端有更新"通知 → 触发 pull
```
- **拉取**：`since_cursor` 之后的变更，增量返回，客户端本地回放合并。
- **推送**：客户端出站批量上送，服务端按版本向量判断冲突。
- **通知**：WebSocket 仅在联网时作为"新变更提醒"，请求由客户端发起，简化一致性。

### 6.3 断网 / 弱网
- 离线期间所有操作进 Outbox；恢复联网自动重推，指数退避重试。
- 附件：先传元数据与引用，字节按需/后台分块上传。

### 6.4 版本号模型（三套独立版本，勿混淆）

同步收敛的正确性取决于**分清三套版本**，它们各司其职：

| 版本 | 属于谁 | 怎么来 | 怎么变 | 参与冲突判断？ |
|------|--------|--------|--------|----------------|
| **base（基线）** | 客户端持有 | 从服务端拉取当前权威版本，作为某次编辑的起点 | 每次 pull 刷新；编辑期间**冻结为定值** | ✅ 参与（对比用） |
| **本地草稿版本** | 客户端内部 | 本地每次保存 +1（v6→v7→…），仅本机私有 | 只增不减，直到提交 | ❌ 不参与 |
| **服务端权威版本线** | 服务端 | 每次成功合并提交 +1（v5→v6→…）持续增长 | 只增不减 | ⚠️ 服务端拿它跟 base 比 |

**核心规则：**
- **base 不是服务端的概念**，服务端持有的是一条**持续推进的权威版本线**，不是固定起点。
- 本地草稿号（A 改 20 次 → v25）**从不参与冲突判断**——服务端只关心你 push 时声明的 `base`。
- **冲突判定**：服务端拿客户端声明的 `base` 对比**服务端当前权威版本**。两者不同（说明该 base 之后已被别的事务推进）→ 判定冲突，走合并。
- 任何设备都**无权自行产生全局权威版本号**——发号权只属服务端，保证全网顺序唯一、可收敛。

### 6.5 合并语义：git 式 rebase 线性化 + diff3 三方合并

- **底层原理与 git 一致**：本地草稿 ≈ 本地分支 commit；服务端权威线 ≈ origin/main；pull 更新 ≈ 本地重放到新基线（**rebase**）。
- **历史保持线性**（v5→v6→v7→…），**不保留 merge 提交节点**——每接受一次合并，服务端产生一条干净的权威版本。
- **冲突用 diff3 三方合并**（base + 两个新版本）解决，比纯 rebase 更友好。
- **与 git 的关键差异（本系统更强）**：无论 rebase 还是合并，**任何路径都不静默丢字**——合并失败的败方内容也保留为修订，不消失。

### 6.6 冲突处理规则（不丢数据优先，逐层降级）

1. **直接应用（无冲突）**：`base` 与服务端当前一致 → 直接落库，`version+1`。覆盖 95% 场景。
2. **字段级合并**：标题、正文、标签、附件分别比较。A 改标题、B 改正文 → 各取所长，两边修改都保留。
3. **diff3 三方合并（同字段冲突）**：两边都改同一字段 → base+两新版本 三方合并；改动不重叠 → 自动合并成功，产生一条权威版本。
4. **双版本保留（自动合并失败，需人工）**：`version` 较大者生效为当前内容；败方完整存为一条带 `conflict` 标记的新修订；UI 提示"本笔记有冲突需核对"，用户可逐段选择/直接采纳一方。**绝不静默二选一**。
5. **LWW 兜底（极端保障）**：`version` 较大者胜出，但败方内容仍保留为修订，可在历史中找回——**任何路径都不丢字**。

> 判定依据只有 `base` 是否撞车；**保存时间、修改次数均不作裁决依据**。

### 6.7 pull 更新后客户端行为

- **无未提交草稿时**：pull 只是**追加**远端新版本，本地历史完整无丢失。
- **有未提交草稿时**：先对未同步草稿与新版本做 **diff3 合并**，产出一条权威 Revision；本地草稿的最终内容保留为修订，**用户看不到的只是中间草稿步骤，不是内容**。
- **保留策略（可配置，见 §11）**：全量保留 / 智能压缩（默认）/ 快速清理。无论哪档，pull **只追加、不删除**。

## 8. 笔记编辑器与内容格式（需求 3）

### 8.0 编辑器技术选型（已定案）

> **结论：`flutter_quill`（Delta 编辑模型）+ `markdown_quill`（Markdown↔Delta 双向转换）+ `flutter_markdown`（源码/只读渲染），守住 canonical = Markdown。**

- **存储层正本恒为 Markdown**；同步/历史/搜索都基于 `content_markdown`（定案）。
- **编辑模型用 Delta（JSON）**：Quill 以 Delta 为内部模型，能以 JSON 无损往返保证 WYSIWYG 编辑体验，天然安全（存库无需消毒）[$TRAE_REF](https://www.rapidevelopers.com/flutterflow-tutorials/how-to-create-a-document-editor-in-flutterflow)。
- **Markdown ↔ Delta 双向转换**：读笔记 `Markdown → Delta`，保存 `Delta → Markdown` 再落库——持久层永远是 Markdown。
- **双轨**：WYSIWYG（Quill）为主 + 源码视图（直接编辑 Markdown 文本）。切换源码改的是纯 Markdown，切回 Quill 重新 `Markdown → Delta`。

**选型对比**

| 方案 | 编辑体验 | Markdown 往返 | 维护 | 结论 |
|---|---|---|---|---|
| **flutter_quill + markdown_quill** | WYSIWYG 成熟 | 可转换 | 好，生态大 | **推荐** |
| appflowy_editor | 块编辑器、Notion 风 | 绑定其块模型 | 中（AppFlowy 主推） | 备选 |
| flutter_markdown（纯渲染） | 差，仅预览 | 天然源码 | 好 | 仅作展示/只读 |
| super_editor | 可组合 | 需自写桥接 | 平均 | 偏底层 |

**风险与缓解**：官方明确提示 Markdown↔Delta 转换 *experimental*[$TRAE_REF](https://pub.dev/packages/wysiwyg_flutter_quill)。
- 仅对**标准 GFM 子集**（标题/列表/粗斜/勾选/代码块/表格）做往返；**复杂内容**（mermaid、内嵌 math）**保留源码模式**不做往返转换。
- 封装为 `EditorBridge` 接口（放 note_core），编辑器实现可替换——若转换质量不达标，可平滑切换编辑内核，不污染上层。

### 8.1 双轨内容体系
- **规范正本 = Markdown**（含扩展语法：附件占位、勾选、代码块、表格 GFM、LaTeX 可选）。
- 视图层 = WYSIWYG（扁平化渲染，所见即所得），支持一键切换到**源码模式**。
- 极简正文 = 默认无富文本控件条，全部靠 Markdown 语义（`#`、`-`、`**`、`[ ]`）形成，降低心智负担。

### 8.2 块模型（为极简 + 未来扩展留余地）
- 每份笔记内部为"块序列"（段落/标题/列表/代码/引用/图片/附件），可映射回 Markdown。
- 配置化离线优先的编辑器内核（Dart 实现），保证手机/桌面渲染一致。

### 8.3 大/多笔记性能
- 千篇级别规模打开秒开（SQLite 索引 + 懒加载）。
- 长文档分段渲染，滚动虚拟化。

### 8.4 表格能力（档位 B：可视化 GFM 表格，已定案）

> **存储 = 纯 GFM Markdown 表格**；**渲染层 = 可视化表格控件**。视觉操作只在渲染层生效、不落盘，守住 canonical=Markdown 约束。

- **能力范围**：单元格就地编辑、加行/删行/加列/删列、调整列宽、行列对齐（left/right/center）、表头指定。
- **范围边界（GFM 限制）**：不支持单元格内嵌多段落/图片/合并单元格/复杂排版；对齐仅列级，不做自由对齐。
- **实现要点**：编辑器内核识别 Markdown 表格块 → 渲染为可编辑网格控件；所有视觉操作（拖列宽等）转换回标准 GFM 语法落盘，不引入私有格式。
- **双轨一致**：源码模式下直接编辑管道语法；WYSIWYG 模式下可视化编辑，两者实时同步。
- **投入产出**：实现成本中；用户体感接近专业表格，却无富表格(C)带来的编辑器内核、同步、修订全链路改造。
- **远期（暂不做）**：富表格（单元格内嵌块/合并单元格）需破坏 Markdown 正本，待产品验证后再评估。

## 10. 多媒体附件（需求 5）

- **内容寻址 Blob**：`sha256` 命名存储，跨设备/跨端去重，节省同步带宽。
- 类型：图片、PDF、音频、视频、任意文件。
- 图片自动生成缩略图；音频/视频生成可预览卡片。
- 笔记内嵌渲染：Markdown `![](obs://<hash>)` 占位 → 编辑器渲染媒体卡片。
- GC：服务端定期清理引用计数为 0 的孤儿 Blob；客户端本地可按需清理已同步的大附件。

## 10.5 存储技术路径（定案）

> 本专题经研讨定案，涵盖总体选型、附件存储、云端元数据库、两端表结构与容量。

### 总体选型：一个业务核心，按端选存储后端

- 采用 **DAL 数据访问层抽象 + drift（Dart 版 SQLite ORM）**。
- 笔记元数据（标题/正文/标签/版本）→ 全端进 **SQLite**。
- 桌面/移动：drift 落原生 SQLite；Web：同一 drift 跑在 WASM + IndexedDB 上。
- 收益：**同步引擎、冲突解决、搜索逻辑只写一次，三端复用**。
- 附件字节 → 独立 Blob 存储，不进 SQLite，业务层只看 ID/hash。

### 附件存储：两端分开存，但都按 sha256 内容寻址

| | 客户端 | 服务端 |
|---|---|---|
| 元数据 | `attachments` 表只存引用+hash | `blob_objects`（sha256 主键 + refcount） |
| 字节 | 本地 blob 目录（`~/sui/blobs/`，按 hash 分片） | 默认服务端磁盘（`/data/blobs/` 分片） |
| 特点 | BlobStore 接口（本地文件 / Web 沙箱） | BlobStore 接口（本地盘 / S3 可切换） |

- **字节不随笔记同步走、按需拉取**；`sha256` 天然去重；服务端靠 refcount + GC 做去重中心。
- 服务端默认 `BLOB_STORE=local` 存本地磁盘（`/data/blobs/` 分片），零运维贴合自托管；
  抽象 `BlobStore` 接口 + 环境变量切后端：`local ↔ s3`（MinIO/COS）。**元数据只记 sha256+refcount，换后端时元数据库零改动**。
- 本地磁盘要点：分片目录（`blobs/ab/`）、哈希幂等、refcount GC、定时备份 blobs 目录。

### 云端元数据数据库：默认 SQLite，留 PostgreSQL 的接口

- 表结构与客户端**共用 schema 完全对齐、各自私有字段各留各的**。
- 同步协议**只走两边的公共字段；私有状态（outbox/cursor/refcount）不进协议**。
- 现在用 SQLite 落地（自托管零运维），通过 `Store` 接口保留换 PostgreSQL 的路，**不预付抽象成本**。

**共用 schema（进同步协议）** —— `notes`／`revisions`／`notebooks`／`attachments`(引用)
**客户端私有** —— `outbox` · `base` · 本地草稿号 · `last_pull_cursor`
**服务端专属** —— `devices` · `sync_cursors` · `blob_refs` · 权威版本线

### SQLite 容量确认

- 单库默认上限约 1TB，可支撑**几十万到上百万条笔记**；个人场景通常 <1 万篇，**非瓶颈**。
- 真正撑大库的是**附件**，故设计上附件已移出 SQLite，库保持瘦身。
- 容量焦虑无必要；重点放在同步一致性与搜索体验。

## 11. 笔记历史查看与恢复（需求 6）

### 11.1 历史版本策略（已定案）

> **权威历史 = 服务端合并提交记录（Revision Chain by Server）。**
> 客户端未同步的改动，只在**本机临时可见**（本地草稿暂存区）。
> 一旦完成同步（push 成功 / pull 合并），本地草稿并入服务端版本线，**历史从此以服务端版本为主**，本地草稿中间步骤不再作为独立历史条目展示（内容不丢，作为修订保留可查）。

- **历史单一来源**：所有设备回看的是同一份服务端提交链，无"各端历史不一致"困惑。
- **未同步草稿安全**：同步前是本机临时可回看（标"未同步，仅此设备可见"，不自动丢弃）；同步后并入权威线。
- **UI 清澈**：历史时间轴只有一条线（服务端权威链），不混入本地/服务端两套。
- **本机私有草稿**：各设备只看到自己离线编辑的中间步骤，彼此不可见（默认不上传）。

### 11.2 修订记录写入

- **双写**：每次保存写一条 `Revision`——同时存 **内容快照**（按间隔/按需，如每 20 版或每改动≥阈值）与 **diff 增量**（小改动高频）。
- 历史时间轴 UI：滑块/列表浏览任一历史版本，可**查看 Diff**、**一键恢复**（恢复即新建版本，不覆写当前）。
- 服务端保留所有修订（可选配额/保留策略），客户端默认只保留近期修订，按需从服务端拉取完整历史。

### 11.3 保留策略（可配置）

| 档位 | 行为 | 场景 |
|------|------|------|
| **全量保留** | 每次草稿步骤都留 Revision | 个人笔记，历史最完整 |
| **智能压缩（默认）** | 连续同段小改动合并成一条，跨大改动保留 | 历史够回溯、存储可控 |
| **快速清理** | 仅保留权威历史 + 合并结果，草稿中间步骤丢弃 | 存储最小 |

> pull 永远**只追加、不删除**；"内容还在不在"与"中间步骤序号看不看得到"是两回事——折叠步骤 ≠ 丢内容。
